# Geospatial File Measurement API

A small, self-contained FastAPI service that accepts a **zipped Shapefile** or a
**KML** file, extracts every feature, picks an appropriate metric projected
CRS, and computes **polygon areas (m², km²)** and **LineString lengths
(m, km)**.  Results are persisted in SQLite so they remain available across
independent API requests and server restarts.

The single most important correctness rule of this project is:

> **Never calculate area or length directly from longitude/latitude degrees.**

A degree of longitude is ~111 km at the equator and ~0 m at the poles, so any
"area" computed in degree² is meaningless.  Every measurement in this service
is computed on a **reprojected copy** of the geometry in a CRS whose unit is
the **metre**.

---

## Project Overview

The service was built as a submission for the *Geospatial File Measurement API*
assignment.  It demonstrates:

* **Multipart file upload** with strong validation (extension, magic bytes,
  size limit, ZIP-path-traversal protection).
* **Two format readers**:
  * **Shapefile (ZIP)** -- extracts `.shp / .shx / .dbf`, reads `.prj` when
    available, rejects ambiguous multi-shapefile archives.
  * **KML** -- parsed via the pure-Python `fastkml` library, because the
    Fiona/GDAL build in this environment does **not** register the KML driver.
    This is the *reliable fallback* the assignment explicitly permits.
* **CRS strategy** -- detects the source CRS, picks a UTM zone for
  geographic input (via `GeoDataFrame.estimate_utm_crs()`), verifies the
  measurement CRS uses metres, and never overwrites the source geometry.
* **Honest handling of missing CRS** -- when a Shapefile has no `.prj`, the
  service refuses to guess; it returns the features with a clear warning and
  marks measurements as `UNAVAILABLE`.
* **Per-feature resilience** -- a single invalid feature never crashes the
  whole upload.  Invalid polygons are auto-repaired with `buffer(0)` where
  possible; unrecoverable features are skipped with a warning.
* **SQLite persistence** -- every file and every feature row is persisted to
  `data/geospatial.db` so that the API is stateless on the HTTP layer.
* **OpenAPI documentation** at `/docs` automatically generated by FastAPI.

```bash
git clone https://github.com/<your-account>/geospatial-file-measurement-api.git
```

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

## API Documentation

### `GET /`

Interactive HTML preview page.  Drag-drop a `.zip` or `.kml` file, see the
file info, see every feature on a Leaflet map, and read the measurements JSON
next to the map.  Not included in the OpenAPI schema (it is a UI, not an API
contract).

### `GET /health`

Liveness check.  Returns:

```json
{"status": "ok", "service": "geospatial-file-measurement-api", "database": "ok"}
```

### `POST /api/files/`

Upload a Shapefile (.zip) or KML file as multipart form-data under the field
name **`file`**.  The whole upload is read into memory; the request is
rejected with `413` when it exceeds `GEOSPATIAL_MAX_UPLOAD_BYTES`.

On success the response is HTTP **201 Created** with:

```json
{
  "id": "321a21dd99e942e49dd37a652cfb50fa",
  "filename": "survey.kml",
  "feature_count": 1,
  "crs": "EPSG:4326",
  "source_crs": "EPSG:4326",
  "measurement_crs": "EPSG:32644",
  "status": "COMPLETED",
  "warnings": [],
  "created_at": "2026-10-09T13:35:34.203541+00:00"
}
```

Errors:

| Status | Reason                                                          |
| ------ | --------------------------------------------------------------- |
| 400    | Magic-byte signature does not match the extension.             |
| 413    | Upload exceeds the configured size limit.                       |
| 415    | Extension is not `.zip` or `.kml`.                              |
| 422    | ZIP without a Shapefile, ambiguous multi-shapefile ZIP, malformed KML, or other geospatial processing failure. |
| 500    | Unexpected internal error (no stack trace is exposed).          |

### `GET /api/files/{file_id}/`

Return the persisted file record.  `404` when the id does not exist.

### `GET /api/files/{file_id}/measurements/`

Return measurements for every feature in the file.  Example:

```json
{

    },
    {
      "feature_index": 1,
```

### Processing pipeline

```
HTTP POST /api/files/
   │
   ▼
1. Validate upload           (services/validation.py)
   • extension in {.zip, .kml}                      -> 415 if not
   • first bytes match ZIP/KML signature            -> 400 if not
   • size <= MAX_UPLOAD_BYTES                       -> 413 if not
   │
   ▼
2. Save raw bytes to data/uploads/<uuid>.<ext>
   │
   ▼
3. Read geospatial data      (services/readers.py)
   • .zip -> find complete Shapefile set (.shp+.shx+.dbf)  -> 422 if missing
                                                          -> 422 if ambiguous
   • extract into a TemporaryDirectory
   • gpd.read_file() -> GeoDataFrame with CRS from .prj
   • .kml -> fastkml.parse() -> walk Placemarks -> Shapely shapes
   • promote homogeneous GeometryCollection -> Multi*
   • drop null/empty geometries with a warning
   │
   ▼
4. Build pyproj CRS for source
   │
   ▼
5. Select measurement CRS    (services/crs.py)
   • source None     -> None + warning
   • source projected & metric  -> source
   • source projected & non-metric -> None + warning
   • source geographic -> estimate_utm_crs()
   • emit wide-extent warning when span > 6° longitude
   │
   ▼
6. Persist file record       (database.insert_file_record)
   │
   ▼
7. Per-feature processing    (services/measurements.measure_geometry)
   • Point/MultiPoint              -> NOT_REQUIRED
   • Polygon/MultiPolygon          -> area_m2 + area_km2 (COMPLETED)
   • LineString/MultiLineString    -> length_m + length_km (COMPLETED)
   • other                          -> UNAVAILABLE
   • invalid geometry              -> buffer(0) repair path, warning
   • reprojected copy              -> never mutates source geometry
   • NaN/Inf                       -> filtered, never reaches JSON
   │
   ▼
8. Persist each feature row  (database.insert_feature)
   │
   ▼
9. Return the file-info dict (HTTP 201)
```

## CRS Strategy

This is the most important correctness-critical part of the assignment, so it
is documented in detail.

### Why measurements are not calculated in degrees

Longitude and latitude are angles, not lengths.  At the equator, one degree
of longitude is roughly 111 km; at 60° N it is roughly 55 km; at the poles
it is zero.  Any area computed directly in `degree²` therefore depends on
latitude and is **not a geometric area** -- it is a meaningless number that
gets smaller the closer you are to a pole.

The same is true for length: a "1 degree" LineString could be anywhere
between 0 m and 111 km long depending on its latitude.

### How the service picks a measurement CRS

`services/crs.py::select_measurement_crs` implements this logic:

| Source CRS                                  | Strategy                                                              |
| -------------------------------------------- | -------------------------------------------------------------------- |
| `None` (no `.prj`, no KML CRS hint)           | **Refuse to guess.** Return `None` and a warning.                    |
| Projected + linear unit is the metre         | **Use the source CRS directly** -- no reprojection needed.           |
| Projected but linear unit is not the metre    | Refuse -- unit-mislabelling risk.  Return `None` and a warning.      |
| Geographic (e.g. EPSG:4326)                    | **`GeoDataFrame.estimate_utm_crs()`** picks the right UTM zone for the dataset's extent. |
| Anything else                                 | Refuse -- mark `UNAVAILABLE`.                                         |

### Verification that the measurement CRS is metric

Even after `estimate_utm_crs()` returns a CRS, we re-check its linear unit
through `services/crs.py::is_metric` / `services/measurements.py::_crs_is_metric`.
UTM CRSs use the metre (good), but some legacy projected CRSs use the US
survey foot or the international foot -- in those cases we **refuse to
label measurements as m / m²** and mark the feature `UNAVAILABLE`.

### Source geometry preservation

Every measurement runs on a *reprojected copy*:

```python
from shapely.ops import transform as shp_transform
from pyproj import Transformer
transformer = Transformer.from_crs(src, dst, always_xy=True)
geom_m = shp_transform(transformer.transform, geom)
```

`shapely.ops.transform` constructs a brand-new geometry; the source
geometry is **never** mutated.  The API response serialises the **original**
geometry (in the source CRS), so `feature.geometry.coordinates` always
contains lon/lat for an EPSG:4326 input, not the UTM coordinates used for
the calculation.

### KML

KML coordinates are always WGS84 longitude/latitude (the OGC KML spec is
explicit about this), so the service always sets `EPSG:4326` for KML input.
For Shapefile uploads, the source CRS comes from `.prj` if present.

### Missing or unusable CRS

When the source CRS is missing (a Shapefile shipped without a `.prj`), the
service **does not silently assume** EPSG:4326.  Doing so would silently
mislabel unknown projected coordinates as lon/lat and produce wildly
incorrect measurements.  Instead:

* The file is still uploaded and persisted (HTTP 201).
* `source_crs` and `measurement_crs` are both `None`.
* The `warnings` field explains the situation.
* Every feature's `measurement_status` is `UNAVAILABLE` and
  `measurements` is `{}`.

### Limitations of a single UTM zone

`estimate_utm_crs()` returns one UTM zone -- the one that minimises the
total distortion over the dataset's bounding box.  This is excellent for
locally-scoped data (a few km to a few hundred km across).  For globally
distributed or very wide data, a single zone introduces distortion at the
edges:

* The dataset spans more than ~6° of longitude -- the eastern and western
  fringes leave the zone's "well-conditioned" range.
* The dataset crosses the equator -- UTM zones split into north/south
  variants; one zone can't cover both hemispheres.

`services/crs.py::_warn_if_wide_extent` detects this and emits a warning,
but the service still produces a best-effort measurement using the chosen
zone.  A future improvement (see *Future Scope*) would split the data into
per-zone groups for higher accuracy on global datasets.

## Design Decisions

### Why FastAPI?

* **First-class OpenAPI**: routes, status codes and response models are
  auto-documented at `/docs`.  No extra annotation work.
* **Native async support**: not used here (we process synchronously per the
  assignment), but trivial to add later for large-file streaming.
* **Dependency-injection container**: not heavily used here, but useful for
  adding auth / rate-limiting middleware without touching route code.
* **TestClient**: the same app object is exercised by pytest without
  needing a separate Gunicorn process.

Alternative considered: **Flask**.  Excellent and well-understood, but
OpenAPI generation requires an extra library (e.g. `flask-smorest` or
`apispec`) and async support is bolted-on rather than native.

### Why GeoPandas + Shapely + PyProj?

These three are the de-facto Python geospatial stack:

* **GeoPandas** is a thin layer over Shapely geometries that adds the
  concept of a CRS-aware DataFrame.  It exposes
  `GeoDataFrame.estimate_utm_crs()` -- the cleanest way to pick a UTM zone
  for an arbitrary dataset.
* **Shapely** is the workhorse for geometry operations (`area`, `length`,
  `is_valid`, `buffer(0)` repair, `__geo_interface__`).
* **PyProj** is the only Python library with a PROJ-backed
  `Transformer.from_crs(src, dst, always_xy=True)` -- the correct way to
  reproject coordinates without axis-order surprises.

Alternative considered: **GDAL Python bindings directly**.  More powerful
for low-level work but more error-prone (C-level APIs, opaque error
messages, no `__geo_interface__`).

### Why SQLite?

* **Zero config**: file-backed, ships with Python's stdlib.  Perfect for an
  assignment of this size.
* **Transactional**: `with conn:` blocks give us ACID per-file persistence
  with no extra infrastructure.
* **Easy to inspect**: a developer can `sqlite3 data/geospatial.db` and
  inspect rows directly during debugging.

Alternative considered: **PostgreSQL + PostGIS**.  The right choice for a
production geospatial service, but introduces a server dependency that
would slow down review.  The schema and queries here are simple enough
that porting to PostGIS would be straightforward.

### Why fastkml + lxml instead of GDAL's KML driver?

The GDAL build exposed through `fiona.supported_drivers` in this
environment does **not** register the KML driver:

```python
>>> import fiona
>>> fiona.supported_drivers
{'ESRI Shapefile': 'rw', 'GPKG': 'rw', 'GeoJSON': 'rw', ...}   # no KML
```

The assignment explicitly anticipates this:

> *If you choose an alternative implementation for reading KML because the
> available GDAL/Fiona installation does not support the KML driver,
> implement and test a reliable fallback rather than silently leaving KML
> processing broken.*

`fastkml` is a pure-Python KML parser built on `lxml`.  It exposes
Placemark geometries through `__geo_interface__`, which `shapely.geometry.shape`
reads directly.  The fallback is fully exercised by the test suite -- the
KML tests use real KML documents written by the test fixtures, parsed by
the real `fastkml` code path, and measured by the real CRS+measurement
pipeline.

### Why synchronous processing?

The assignment asks for synchronous processing unless there is a
compelling reason to go async.  Our synthetic test polygons upload in
milliseconds and the maximum configured upload is 50 MiB.  Introducing
Celery/Redis would add operational complexity without measurable benefit
at this scale.  See *Future Scope* for the path to async.

### Why per-row resilience instead of fail-fast?

A real-world Shapefile can contain thousands of features.  One bad
geometry should not poison an otherwise-good upload.  The pipeline
collects warnings per feature and continues, so the caller gets the
maximum amount of usable data with a clear list of what failed.

```bash
python3 scripts/smoke_demo.py
```

It uploads a tiny KML polygon, prints the file-info and measurement
responses, and exits 0 on success.

## Learning

Building this project taught the following concepts and engineering skills:

### Geospatial

* **CRS is not just a string**.  Two CRSs can both be called "WGS 84" yet
  differ in axis order (lat-first vs lon-first) or in the linear unit they
  use.  `pyproj.CRS.axis_info` exposes the unit explicitly; never trust
  the EPSG code alone to know what a "1.0" means.
* **The axis-order trap**.  In the past, the standard GIS convention was
  `(x=lon, y=lat)`.  EPSG itself uses `(lat, lon)` for EPSG:4326 (per the
  official registry).  `Transformer.from_crs(src, dst, always_xy=True)`
  forces the GIS convention and avoids the most common reprojection bug.
* **`buffer(0)` as a repair tool**.  Self-intersecting polygons
  (bow-ties) are a common real-world problem.  Shapely's `buffer(0)`
  rebuilds the polygon from its segments and fixes many topological
  errors without changing the valid vertices.
* **GeoJSON is the universal interchange**.  Every Shapely geometry
  implements `__geo_interface__`, which is the same contract that
  `fastkml`'s geometry objects implement.  This is why a third-party
  library (fastkml) plugs into Shapely with one line of glue.
* **UTM is local**.  The UTM system splits Earth into 60 longitudinal
  zones, each 6° wide, each with its own projection.  A single zone is
  fine for data that fits inside it; globally distributed data needs a
  different strategy (e.g. equal-area CRS or per-zone splitting).

### Backend engineering

* **Magic bytes beat Content-Type**.  The `Content-Type` header and the
  uploaded filename are both client-controlled and trivially spoofable.
  Inspecting the first few bytes of the file (`PK\x03\x04` for ZIP,
  `<?xml` for KML) catches mislabelled or malicious uploads cheaply.
* **ZIP path traversal is a real attack**.  A ZIP member named
  `../../../etc/passwd` would, when extracted naively, escape the temp
  directory and overwrite system files.  Rejecting absolute paths and
  `..` segments *before* extraction is non-negotiable.
* **Clean error contracts beat stack traces**.  Every exception that
  reaches the API boundary is a `GeoAPIError` subclass with an
  `status_code` and a user-friendly `detail`.  Generic exceptions are
  caught at the top level and replaced with a 500 so a developer never
  sees a stack trace from a public endpoint.
* **SQLite is enough for the long tail**.  Production-grade services
  tend to reach for Postgres too early.  For this assignment, a single
  file with `PRAGMA foreign_keys = ON` and `ON DELETE CASCADE` covers
  every requirement and stays trivially inspectable with `sqlite3` CLI.
* **Test fixtures should be programmatic**.  Committing binary sample
  files creates silent bit-rot and adds weight to the repo.  Building
  Shapefiles and KML documents in `conftest.py` from Shapely geometries
  keeps the tests self-describing and immune to upstream dataset changes.

## Future Scope

Realistic, scoped improvements that would carry this service closer to
production:

1. **Asynchronous processing for large files**.
   Move the geospatial pipeline to a background worker (RQ, Celery, or
   FastAPI's `BackgroundTasks` + a process pool).  `POST /api/files/`
   would return `202 Accepted` with a job id; clients would poll
   `GET /api/files/{id}/` until `status` becomes `COMPLETED`.  This is
   only worth doing once typical upload sizes exceed the synchronous
   request budget -- the assignment's 50 MiB limit is fine synchronously.

2. **Pagination of measurements**.
   Files with thousands of features would produce multi-megabyte JSON
   responses.  Add `?limit=` / `?offset=` query parameters and a
   `Link: rel="next"` header.

3. **Authentication**.
   Add an `Authorization: Bearer ...` middleware that gates every
   endpoint except `/health`.  Per-user file ownership columns in the
   `files` table.

4. **Cloud / object storage for raw uploads**.
   Replace `data/uploads/` with an S3 (or GCS / Azure Blob) bucket, so
   raw uploads survive container restarts and can be reprocessed later.
   Useful for audit trails.

5. **Additional geospatial formats**.
   * GeoJSON (trivial -- Shapely reads it directly).
   * GeoPackage (`.gpkg`) -- a single-file container that supports
     multiple layers and modern CRS handling.
   * DXF / CAD -- relevant for surveying use cases.

6. **Multi-zone UTM for very wide datasets**.
   Detect when a geographic dataset's longitude span exceeds 6° and
   split features into per-UTM-zone groups, measuring each in its own
   zone, then aggregating.  This eliminates the edge distortion a single
   UTM zone introduces on global data.

7. **Per-feature validity diagnostics**.
   For invalid geometries, return a structured `warnings` entry with
   the GEOS validity reason (e.g. "Self-intersection at ...").  Useful
   for callers that want to repair the source data upstream.

8. **Containerised deployment**.
   A `Dockerfile` + `docker-compose.yml` for one-command reproducible
   runs.  (Skipped from the initial submission to keep the surface area
   focused on the assignment's core requirements.)

9. **Streaming uploads for very large files**.
   Replace the in-memory `file.file.read(MAX + 1)` with a chunked
   `StreamingUpload` reader so a 1 GiB upload does not need 1 GiB of RAM
   before validation.

10. **OpenAPI examples + redoc**.
    Embed `example=` metadata on the Pydantic response models so the
    Swagger UI shows representative payloads inline.
